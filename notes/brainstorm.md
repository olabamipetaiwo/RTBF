# Brainstorm: Strengthening the IEEE S&P Submission

Ideas to elevate the paper beyond an empirical audit into a contribution reviewers cite as a framework.

---

## 1. Taxonomy of erasure failure mechanisms

The data reveals distinct reasons erasure fails, not just that it does. Classifying these turns raw results into a reusable framework.

**Layer mismatch** — User deletes Surface A, data persists in Surface B. The user's mental model of "where my data lives" doesn't match the platform's actual persistence architecture.
- Claude: deleting a conversation leaves auto-generated memory entries untouched (E1 always fails, memory-targeted methods always succeed)
- ChatGPT: deleting conversations doesn't remove the Memory entries they generated
- Copilot: deleting a conversation (E2) fails because Saved memories are a separate layer

**Scope mismatch** — Deletion targets the right layer but the wrong granularity, or the operation's actual scope doesn't match what the UI implies.
- Gemini E4: user deletes the exact Saved info item that holds the data, UI confirms deletion, data still recoverable
- Copilot E4 on I2: same pattern, targeted memory deletion doesn't stick
- Gemini E5: "delete ALL Saved info" paradoxically fails on I1 chat-injected data (scope covers the layer but misses a sub-path)

**Method blindness** — The erasure action never reaches the persistence layer at all. The platform acknowledges the request but doesn't act on it.
- ChatGPT NL forget: responds "I've forgotten that" but Memory entries remain unchanged
- Gemini NL forget on I2: claims compliance, nothing deleted
- Gemini Keep card: 7/133 chat-based erasure requests triggered a Google Keep permission card instead of any deletion action

**Compliance by absence** — No persistent memory exists, so nothing survives. Trivially compliant but not by design.
- Perplexity (free tier): memory is tier-gated behind Pro
- DeepSeek: no memory UI or persistence layer exists

**Injection-dependent resistance** — The same erasure method succeeds or fails depending on how the data was originally written.
- Copilot: NL forget works on I1 (chat) but fails on I2 (memory instruction)
- Gemini: I2 (Saved info) is universally sticky, I1 partially erasable
- Claude: injection type is irrelevant (clean contrast)

---

## 2. "Privacy nutrition label" concept

Before a user discloses sensitive information, a tool could map what persistence layers exist on the platform and what each deletion action actually covers. Generated by probing, not by trusting the platform's documentation. This is a methodology-as-contribution angle: the automated pipeline itself becomes a reproducible framework others can apply to new platforms.

S&P angle: reviewers value reproducible methodology. The testing pipeline (inject, erase, recall with token-based verification) is already more rigorous than most privacy audits in the literature. Framing it as a generalizable framework (not just "we tested 6 platforms") strengthens the contribution.

---

## 3. User expectations vs. platform reality gap

The survey data (177 participants) quantifies what users *expect* each deletion action to do. The audit data shows what it *actually* does. The gap between these is the core S&P argument: users are making privacy decisions based on incorrect mental models, and the platforms' UIs do nothing to correct this.

Specific angles:
- Users who "delete conversation" expect all traces gone (survey data) vs. memory entries surviving (audit data)
- NL forget feels like the most intuitive approach but is the least reliable
- Even targeted deletion ("delete this specific memory") fails on some platforms (Gemini/Copilot E4)
- The only reliable method (MAXIMAL) requires expert knowledge of every persistence layer

---

## 4. Cross-platform consistency argument

No two platforms handle erasure the same way. A user who learns "delete conversation" works on Claude's memory will incorrectly assume it works on ChatGPT. The inconsistency itself is a security/privacy problem: there's no transferable mental model.

Platform behavior matrix (erasure method x injection type x platform) as a contribution: a reference table showing which combinations work and which don't, across all 6 platforms.

---

## 5. The "acknowledged but not executed" pattern

ChatGPT and Gemini both *say* they've forgotten/deleted when they haven't. This is worse than refusing: the user believes the data is gone. Frame as a deceptive pattern (not necessarily intentional, but the effect is the same).

ChatGPT: "I've updated my memory" / "I've forgotten that" — Memory entries unchanged
Gemini: compliance claims in chat, nothing deleted from Saved info
Copilot: "Memory saved" during injection (57/138), then NL forget fails to undo it on I2

---

## 6. Adversarial angle (light touch)

The CH-I1-E5 pressure test produced a confabulation (`htiw etaicosseven`) under adversarial probing. Not a full adversarial study, but worth citing as evidence that:
- Standard recall probes are conservative (they don't push hard)
- Platforms may leak information under pressure even when standard probes show clean results
- Future work: systematic adversarial recall testing

---

## 7. Framing for S&P specifically

S&P values:
- Novel attack surfaces or threat models (the "memory layer as unintended persistence" is novel)
- Rigorous methodology (token-based verification, automated pipeline, inter-rater reliability)
- Practical impact (affects millions of users of these platforms today)
- Responsible disclosure angle (did we notify platforms? Should we?)

Weaker angles to avoid:
- "We tested 6 platforms" (sounds like a survey, not research)
- Compliance framing (GDPR/RTBF legal analysis — not our expertise, and S&P reviewers want technical depth)
- Pure usability study (that's CHI/USENIX Security, not S&P)

The strongest S&P framing: "AI assistants have created a new class of user data persistence that existing deletion interfaces don't fully reach, and users can't tell."

## 8. Tool / artifact ideas (wild brainstorm)

Things we could actually build that serve users, researchers, regulators, and platforms — not just academic contribution but real-world utility.

### For users

**AI Memory Auditor (browser extension)**
A browser extension that sits on top of ChatGPT/Claude/Gemini/Copilot and shows the user a real-time "X-ray" of their data footprint: what the platform remembers, where it's stored (conversation history vs. memory entries vs. saved info vs. custom instructions), and what each deletion action will and won't erase. Before you hit "Delete conversation," it warns: "This will NOT remove the 3 memory entries generated from this conversation." No more guessing.

**"Delete Everything" button that actually works**
A cross-platform tool that performs MAXIMAL erasure (the only reliable method) with one click. It knows which surfaces to hit on each platform, in which order, and verifies afterward. The user shouldn't need to be a platform architect to fully delete their data.

**Privacy Dashboard / Data Map**
Visual map showing: "Here's what [platform] knows about you, here's where it lives, here's what happens if you delete X." Think of it like a privacy nutrition label but interactive. Could show the gap between what the user thinks will happen and what actually will.

**Erasure Receipt**
After any deletion action, the tool runs a recall probe (like our R1/R2/R3) and gives the user a receipt: "Deletion attempted. Verified: data no longer recoverable" or "WARNING: data still recoverable in [memory/saved info/etc.]." Proof, not trust.

### For researchers

**Platform Memory Probe Framework (open-source)**
Package our entire pipeline (inject → erase → recall with token-based verification) as a reusable, extensible framework. Other researchers add a new platform by writing one flow module. Standardized output format, automated scoring, built-in inter-rater reliability computation. The "OWASP ZAP but for AI memory privacy."

**Longitudinal Memory Decay Monitor**
Does erasure degrade over time? Do platforms silently re-learn deleted facts from conversation patterns? A tool that runs periodic recall probes (weekly/monthly) on previously erased data and tracks whether deletion is durable or whether data "regrows." Nobody has studied this.

**Cross-platform Memory Fingerprinting**
Test whether data deleted on Platform A resurfaces on Platform B when the same account email is used. Do platforms share memory through Microsoft/Google/OpenAI account graphs? Our study already uses isolated accounts, but a dedicated cross-platform leakage test would be novel.

### For regulators / policy

**Automated RTBF Compliance Tester**
A tool regulators (or their auditors) can point at any AI platform to get a compliance score: "This platform correctly erases data via N of M available deletion methods." Outputs a standardized report. Could be the basis for an industry benchmark or certification.

**Erasure Transparency Scorecard**
Public-facing scorecard rating each platform on: (a) does deletion actually work, (b) does the UI accurately communicate what deletion does, (c) is there a gap between user expectations and platform behavior. Updated periodically. Pressure through transparency.

### For platforms

**Memory Architecture Linter**
A tool platforms run against their own systems to detect "layer mismatch" vulnerabilities before users find them. "Your 'delete conversation' handler doesn't cascade to the memory extraction pipeline" — caught at development time, not by a research paper.

**Deletion Completeness Test Suite**
CI/CD integration: when a platform ships a new memory feature or changes its deletion flow, this test suite injects known data, runs every deletion method, and verifies erasure. Regression testing for privacy. "Your latest deploy broke erasure for I2 injection via E4."

### Wild / moonshot

**Universal AI Data Portability + Deletion Protocol**
An open standard (like OAuth but for AI memory) where platforms expose: 
(a) what they remember about you (structured), 
(b) granular deletion endpoints for each persistence layer, 
(c) verification endpoints that confirm deletion.

Users or their agents interact through one API regardless of platform. Pipe dream today, but the inconsistency data from our study is the argument for why it's needed.

**"Forget Me" AI Agent**
An AI agent whose sole job is to manage your data across AI platforms. You tell it "I no longer want any AI to know my medical history" and it navigates to each platform, identifies relevant memories, executes the right deletion method per platform (because each one is different), verifies, and reports back. It uses our taxonomy to know which method to use where.

**Memory Diff Tool**
Shows what changed in a platform's memory about you after each conversation. "You talked about your dog. ChatGPT added 2 memory entries. Claude added 1. Copilot added 0." Users see the invisible accumulation in real time, conversation by conversation.
