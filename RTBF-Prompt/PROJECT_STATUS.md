## The big picture

One paper, two studies, targeting IEEE S&P 2027. See `timeline.md` for dates.

   about deletion). Statistical analysis is **done**, lives in a separate repo

## Technical audit status

`data/RTBF Experiments.xlsx` is the real, detailed experiment design (more
specific than `context.md`'s summary). Sheets: README (design rules),
ENUMERATION (96 rows, per-platform injection/erasure surface catalog),
MASTER (92 rows, one per (Injection, Erasure) cell, all `NOT RUN` as of this
writing), FILE SUBSTUDY (22 rows), DECISIONS (16 open questions, only Q1-Q2
answered), SETUP (88 total setups: Claude 17, ChatGPT 23, Gemini 14,
Copilot 14, Perplexity 14, DeepSeek 6). Only dry runs have happened so far;
Q2 in DECISIONS confirms those don't count, everything reruns for real data.

Settled protocol decisions, 2026-08-24 (written into the file's README
sheet directly):
- ~~**Fresh account per (Injection, Erasure) cell**~~ **SUPERSEDED
  2026-08-26** by the advisor: accounts may now be reused across cells.
  Contamination/attribution is handled entirely by the unique-anchor-and-
  token policy instead (see below) -- not by account isolation. Original
  rationale kept here for the record: the paper's stats plan assumes
  independent observations across cells, and a shared account risks residue
  from one cell leaking into the next cell's baseline; this was accepted as
  a real risk for the *statistical* independence assumption even under the
  new policy (unique anchor+token solves *attribution*, not necessarily
  outcome independence -- see the account-policy discussion this session).
  Whether/how the stats plan itself accounts for this (e.g. treating account
  as a clustering variable) is still open, separately from the account
  policy itself. The original residue-as-evidence idea is kept only as a
  possible separate, clearly labeled secondary mini-study.
- **Unique anchor + token per experiment** (2026-08-26, from the advisor):
  terminology is **anchor** = the reusable conversational referent/topic
  (e.g. "the garden bed I just planted") and **token** = the unique
  injected codename attached to it (e.g. "Chomp Sufferer Octagon Couch") --
  this is the opposite mapping from what the code originally called
  "anchor" (the codename). **Full rename completed 2026-08-26**: the
  script itself is now `token_generator.py` (was `anchor_generator.py`),
  its outputs are `token.md` (was `anchor.md`) and
  `data/token_assignment.csv` (was `data/anchor_assignment.csv`), and all
  internal identifiers (`anchor_pool`->`token_pool`,
  `build_anchor_pool()`->`build_token_pool()`, `assign_anchors()`->
  `assign_tokens()`, `N_ANCHORS`->`N_TOKENS`,
  `DISTRACTORS_PER_ANCHOR`->`DISTRACTORS_PER_TOKEN`,
  `ANCHOR_MD_PATH`->`TOKEN_MD_PATH`, plus loop variables and prose) now
  consistently mean "token." The referent (anchor) is now also
  unique per cell, not just the token: REFERENTS expanded from 8 (cycled,
  reused ~11x each) to 100 unique entries, direct-indexed per cell instead
  of modulo-cycled. Reasoning: R3's indirect recall probe deliberately
  never mentions the token (that's the point of "indirect"), so under
  account reuse, two cells sharing both an account and a referent would
  make an R3 response genuinely ambiguous between them -- unique referents
  close that gap. 12 spare entries beyond the 88 assigned; expand the list
  before it's ever exhausted by reruns/new cells. Regenerated and verified
  2026-08-26 (all 88 cells confirmed to get distinct referents).
- **Resurrection check delay: 30 days**, standardized across all 6 platforms,
  sourced from the platforms' own privacy-policy deletion-completion
  commitments (not from Claude's separate ~24h memory-synthesis window).
- **Outcome taxonomy pre-registered**: complied / partial / refused /
  deflected / silently ignored, applied to every reading before full-battery
  runs start. Added as a new "Observed outcome (coded)" column in both MASTER
  (column S) and FILE SUBSTUDY (column L), complementing MASTER's existing
  per-cell "Expected outcome (pre-registered)" column (currently all "TBD").
  Deeper failure-mode themes still emerge inductively afterward, per the
  file's original intent (no fixed FM taxonomy imposed).
- **Trial repetition kept as-is**: n=1 baseline, rerun once if a cell
  deviates from its Expected Outcome before recording it as a finding.

- "Type a message" method cells: precisely identified as the 13 MASTER cells
  whose erasure step is an explicit "NL forget prompt/command" (not I1/I2
  injection wording, which is a separate, non-prompt-set-dependent script).
  Flagged in MASTER col T ("Blocked on prompt set? (2026-08-24)"). The other
  63 MASTER cells + all 12 FILE SUBSTUDY cells (75 total) do not depend on
  the prompt set and can run once DECISIONS blockers clear.
- The 16 DECISIONS-sheet questions (Q3-Q18) are the real critical path
  blocking most platform rows from being run at all. **Q17 (anchor/token
  scheme) is now answered**, revised three times (2026-08-24 twice,
  2026-08-26 once more for the unique-anchor-and-token policy and
  terminology swap above) after direct methodological pushback each time —
  see `token_generator.py`'s docstring "design history" section for the
  full reasoning trail, written to drop into the paper's methods section:
  - Tokens are variable-length (2-4 words, drawn uniformly per token),
    not a fixed 2-word "Project X Y" template — Carlini et al. 2019's canary
    framework (USENIX Security) only requires a quantifiable guess-space, not
    a specific word count or "Project"-style carrier.
  - Category exclusion is deliberately narrow: weapon/drug/explicit-sexual-
    content/profanity only (the actual platform-filter-trigger risk Q17's
    "non-sensitive" clause is about), plus a 4-word slur/explicit-term
    denylist. An earlier draft over-restricted on topic (health, crime,
    religion, mortality, politics all denylisted via ~90 words after 9 rounds
    of manual patching that never converged) — dropped as overreach that hurt
    naturalism without serving the actual filter-avoidance rationale.
  - Disclosure/injection text is now injection-type-aware: I1 cells get an
    offhand mention with no request to remember, I2 cells get an explicit
    "please remember" instruction, I3 cells get a settings-field-style note,
    FILE cells get a document-embed line (placeholder pending Q14's PDF
    template). Reusing one phrasing for I1 and I2 alike would have erased the
    methodological distinction between passive-inference and explicit-
    instruction memory tests.
  - Recall-probe text generated in parallel: R1 (direct, two-stage —
    open question, then forced-choice against 3 length-matched distractors
    per Staufer 2025/WikiMem), R2 (settings — fixed inspection procedure,
    not a chat probe), R3 (indirect — token never appears in the probe,
    tests memory leakage into an unrelated task). Each runs same-session and
    cross-session (session is *when*, not different text). See
    `recall_probes.md`.
  - Erasure request text for the 13 prompt-set-dependent cells (MASTER col T)
    is explicitly NOT generated here — still deferred to the qualitative-
    coding pipeline, not invented as a placeholder.
  All 88 cells (76 MASTER + 12 FILE SUBSTUDY) have an assigned token, a
  unique referent, and disclosure text in the xlsx; full lists in
  `token.md` and `recall_probes.md`, machine-readable in
  `data/token_assignment.csv`. Q3-Q16, Q18 still open.

### Cross-platform finding: free-tier accounts, tier-gated RTBF controls (2026-08-28)

**All 6 test accounts (Claude, ChatGPT, Gemini, Copilot, Perplexity,
DeepSeek) are on the free/no-cost tier of their respective platform --
none is a paid subscription.** Logged as DECISIONS Q18.

This surfaced as a real, reportable finding rather than just an account-
provisioning detail: **Perplexity's Memory feature (and everything that
depends on it -- I1/I2 injection, E4/E5 memory erasure, R2 recall) is
entirely inaccessible on the free tier**, confirmed live 2026-08-27 via a
403 Forbidden on the underlying settings endpoints, not just a hidden
UI affordance (see DECISIONS Q7, `tester/flows/perplexity.py`, and the
Perplexity section below). Concretely: a free-tier user cannot inspect,
correct, or erase what Perplexity may have inferred and stored about them
through casual conversation, because the entire memory-management surface
returns an authorization error before it ever renders. **That is itself
an RTBF-relevant access finding, not a limitation of this study's
methodology** -- if the population being studied is "an ordinary user
interacting with these platforms," most such users are on free tiers, and
for at least one of the six platforms, the practical right to inspect/
erase AI-inferred memory is paywalled behind a subscription. Worth
writing into the paper as a substantive cross-platform observation (tier
as an access-to-erasure variable), not just noted as a testing
limitation. The other 5 platforms' memory/erasure surfaces were all
reachable on their respective free tiers -- Perplexity is the one
exception found, not a general pattern across all 6.

Two reusable engineering lessons from this build, generalizable to the
remaining platforms:
- **`goto()` to a URL you're already on can silently no-op** in an Angular
  SPA (the router sees no change, skips re-rendering, leaves stale element
  references) -- `GeminiFlow._goto_fresh()` checks current URL and calls
  `reload()` instead when needed. Caused an intermittent, hard-to-reproduce
  failure in `_delete_saved_info_item()` before being isolated.
- **A menu click can open a second confirmation dialog** that's easy to
  miss -- `_delete_saved_info_item()` initially clicked the "Delete"
  menuitem and silently no-op'd (no error, item just stayed) because that
  only opens a "Delete instructions?" confirm dialog with its own Delete
  button. Same two-step pattern `_delete_all_saved_info()` already handled
  correctly; worth checking for on every "delete" action on every platform
  going forward, not assuming a single click completes it.

**Fixed a real cross-platform bug in `run_cell.py`** discovered while
wiring this up: the orchestrator assumed injection_type has a fixed
UI-surface mapping across all platforms (I1/I2 -> chat, I3 -> settings
field). That's true for Claude/ChatGPT but not Gemini, where I2 ("personal
context injection") targets the Saved-info field, not chat. Fixed by
having each `PlatformFlow` subclass declare `MEMORY_FIELD_INJECTION_TYPES`
(defaults to `{"I3"}`, Gemini overrides to `{"I2"}`) instead of
`run_cell.py` hardcoding the assumption -- see `flows/base.py`.

Still not implemented for Gemini: `_send_nl_forget` (E1 -- same
pipeline-wiring blocker as every other platform's NL-forget cells),
`_delete_all_activity` (E3 -- deliberately left manual, see above),
`_erase_maximal` (E6 -- depends on E3). E3/E6 cells get run by hand rather
than through `run_cell.py` until/unless this changes.

  Settings > Privacy > "Export or delete history" *looks* like E1's

  E3: left deliberately manual rather than extending session capture to
  a second Microsoft domain. Logged as DECISIONS Q21.

**A verification bug cost significant debugging time and is worth flagging
for future platforms**: `read_memory_settings()` initially returned
`page.inner_text("body")`, which also captures the sidebar's conversation
titles in the background -- and conversations get auto-titled from their
content (e.g. a "Remember this: my kayak is called X" message can produce
a conversation titled around X). Since "Delete all memory" explicitly does
NOT delete conversation history (the confirm dialog says so outright),
those lingering titles produced a false "still present" reading even when
the actual memory list was correctly empty, making `_delete_all_memory()`
look flaky/non-deterministic across many test runs when the actual
deletion logic was fine the whole time. Fixed by scoping the read to the
specific dialog containing "View memory" text (`[role="dialog"]` alone
isn't unique either -- this page has ~9 elements with that role, mostly
empty design-system portal placeholders). **Lesson for Perplexity/DeepSeek
builds**: when a stateful check seems to flip randomly between runs,
suspect the verification's scope (is it reading state that a *different*,
undeleted surface also happens to contain) before assuming the underlying
action is unreliable.

Two more UI quirks specific to this platform, documented in
`flows/copilot.py`'s method docstrings rather than repeated here: the
sidebar's per-conversation "..." button's own `bounding_box()` is
misleading (clicking it force-clicks through to the row's navigate-into-
conversation handler instead; the real click target is offset ~28px to
the right of what the button element reports), and the sidebar's open/
closed state persists across page navigations, so code must check for it
rather than assume a toggle button exists.

**Real, confirmed methodological finding, not a code bug**: Copilot's
chat-based memory save (the mechanism I2 relies on) is genuinely
non-deterministic. The exact same injection text, sent in separate runs,
was observed both saving successfully (Copilot's own reply literally says
"Memory saved") and silently not saving at all (no error, no different
reply framing noticed, just nothing added to the facts list) --
reproduced deliberately with identical token/text to rule out a phrasing
or selector issue. `run_cell.py` now checks the reply for "Memory saved"
and retries the injection once if absent, scoped to Copilot's I2 cells
only -- deliberately NOT applied to I1, since I1 is a passive/
conversational disclosure that's methodologically supposed to test
whether the platform infers memory-worthiness on its own; retrying on I1
would turn it into a repeated, more I2-like signal and corrupt that
cell's design. This is a pragmatic mitigation for the automation
pipeline, not a full fix -- worth flagging to the research team as a
platform-level reliability caveat for Copilot's I2 cells specifically
(possibly worth a DECISIONS note on whether/how to pre-register this, and
whether it strengthens the case for the "rerun once if a cell deviates
from Expected Outcome" protocol applying especially here).

Still not implemented for Copilot: `_send_nl_forget` (E3, NL forget
command -- same pipeline-wiring blocker as every other platform's
NL-forget cells), `_delete_via_privacy_dashboard` (E5 -- deliberately
manual, see above), `_erase_maximal` (E6 -- depends on E5). E5/E6 cells
get run by hand rather than through `run_cell.py`, same as Gemini's E3/E6.

### Inject/erase/recall scheduling pipeline, 2026-08-28 (`../tester`)

With all 6 platform flows live-verified, `run_cell.py` needed to stop
doing injection immediately followed by erasure in one script run --
that's fine for selector smoke tests, but wrong for real data collection.
This study's actual design runs each cell as three genuinely separate
events on separate days: **erasure 48 hours after injection, recall 31
days after erasure** (confirmed with the user 2026-08-28: the recall
clock starts at erasure, not injection). Nothing previously tracked
*when* a cell was injected/erased, and `run_cell.py` never ran the R1/R2/
R3 recall probes at all (a literal `# TODO` in the code) or recorded any
outcome back into MASTER.

**Restructured `run_cell.py` into four subcommands**: `inject <cell_id>`,
`erase <cell_id> [--force]`, `recall <cell_id> [--force]`,
`status [cell_id]`. `erase`/`recall` refuse to run before their due date
unless `--force` is passed (used only for this session's own mechanics
verification, never for real cells). New `tester/tracking.py` holds the
scheduling state (`tester/data/run_tracking.json`, local to tester, not
committed into the shared xlsx) -- injected/erasure_due/erased/
recall_due/recalled timestamps per cell, UTC ISO 8601. Human-relevant
results still land in MASTER: Run status (`NOT RUN` -> `INJECTED` ->
`ERASED` -> `RECALLED`), a timestamp breadcrumb appended to the existing
Notes column (non-destructive -- appends, doesn't overwrite), and for
recall specifically the R1/R2/R3 same-session/cross-session columns plus
a rollup Observed-outcome column.

**Confirmed with the user before building**: same-session and
cross-session recall are NOT staggered across two different calendar
times -- same-session recall does not happen immediately after erasure.
*All* recall (both styles) is deferred to the single 31-day-post-erasure
recall phase; "same-session" vs "cross-session" describes two different
probing conditions run *within* that one phase (same-session: one
continuous browser session, `new_conversation()` before each probe;
cross-session: a second, fully separate `with flow_cls()` browser launch
against the same stored cookies, repeating the identical R1->R2->R3
sequence). R1's two stages (open question, then forced-choice only if
the open question didn't surface the token) stay in one conversation
since the forced-choice question is a genuine follow-up; R3 gets its own
fresh conversation so R1's direct probing can't bias its leakage test.

**New `tester/recall_probes_loader.py`** parses
`RTBF-Prompt/recall_probes.md`'s existing, already-generated per-cell
probe table (confirmed live: a clean pipe-delimited markdown table, no
embedded `|` characters) rather than regenerating probes in tester --
regenerating would mean reconstructing `token_generator.py`'s exact
`assigned`/`distractors_by_token` ordering. Also confirmed live while
building this: `erasure_request_sentence()` in `token_generator.py` is a
genuine dead-end draft, not "not wired up yet" -- its own module
docstring (`write_recall_probes_md()`) says NL-forget erasure text comes
from the qualitative-coding pipeline (RTBF-Prompt Step 1-6), not this
script. Every platform's `_send_nl_forget()` stays untouched.

**A real auto-scoring bug found and fixed during verification**: R1/R3
get auto-scored (case-insensitive exact-token substring match against
the reply, tagged `(auto)` for human review, per the user's explicit
choice to auto-score as a first-pass flag rather than capture-only) --
but the R1 forced-choice probe text itself embeds all 4 options
(including the correct token), so a plain substring match produced a
false positive whenever the model hedged/refused by echoing the option
list back rather than genuinely selecting one. Caught live testing
against `DE-I1-E1`: DeepSeek (confirmed to have zero memory/persistence
features) explicitly said "I don't have access to a personal memory of
what you named..." in both the same-session and cross-session replies,
yet the naive scorer still flagged "TOKEN FOUND" because the model's
hedge mentioned the correct option alongside the 3 distractors while
explaining why it couldn't pick one. Fixed: forced-choice only scores
`TOKEN FOUND` if the token appears **and** at most 1 of the 3 distractor
tokens also appears in the reply; otherwise scored `AMBIGUOUS (auto,
forced-choice -- mentions multiple options, see transcript)`, which
correctly does not count as a "leak" in the Observed-outcome rollup.
Re-verified after the fix: `DE-I1-E1` correctly scored `ERASURE
PERSISTED (auto)`.

**Verified end-to-end** (via `--force`, timestamps confirmed exactly 48h/
31d apart, `DE-I1-E1` used since DeepSeek is simplest and fully
verified): `inject` -> tracking + MASTER written correctly; `erase`
refuses without `--force`, succeeds with it; `recall` runs both
sub-phases, writes all 6 R1-R3 columns + Observed outcome + Run status,
saves a full transcript to `tester/transcripts/<cell_id>_recall.json`;
`status` reports phase + due date correctly, both for one cell and for
all tracked cells. Also incidentally hit and worked around a pre-existing,
separate flakiness bug in `deepseek.py`'s conversation-row hover/options-
button visibility (unrelated to this pipeline -- needed for post-test
cleanup, not fixed at the root, just retried defensively) while cleaning
up test conversations afterward. `DE-I1-E1`'s MASTER row and tracking
entry were reverted to their pre-test state afterward since this was a
mechanics verification, not a real study run.

**Deliberate behavior change from the old single-`run()` script, flagged
for visibility**: `inject` now runs even for `blocked_on_prompt_set =
YES` cells (the 13 NL-forget cells) -- previously these were skipped
entirely before injection was even attempted. Rationale: injection
doesn't depend on the qualitative-coding pipeline, only the erasure text
does, so banking the injection timestamp now means the 48h clock is
already running by the time that pipeline's output is ready. `erase`
still refuses for these cells, same as before.

## Working style notes

The user prefers direct, plain restatements of their own points, not added
academic framing/jargon (deductive/inductive, triangulation, etc.) unless
they use those terms themselves. When genuinely unsure about their intent on
something high-stakes for the paper, ask directly rather than guessing.
